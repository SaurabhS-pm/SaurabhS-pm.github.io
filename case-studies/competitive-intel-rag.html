Competitive Intelligence RAG: answering product questions from a competitor's reviews

Five hundred reviews per app across two stores, answered in plain English, with one rule: an ambiguous review is not counted as a positive one.

01

Problem

Product managers monitor competitors by reading reviews, and reading reviews does not scale. A PM trying to work out what users hate about a rival's money-transfer flow wades through hundreds of entries: most irrelevant, many vague, none structured. That happens every sprint, every time a competitor ships, and every time a stakeholder asks what users are saying about X.

The existing answers are a store's own rating summary, which gives a number and no reason, or a social listening tool priced for a marketing team rather than a PM with a question on a Tuesday afternoon.

What was missing was the ability to ask a question in plain English and get an answer grounded in the actual reviews, with the sentiment split stated rather than implied.

02

Approach

Type an app name, optionally a feature area, then ask a question. The tool pulls live reviews from both stores, embeds them on the machine, retrieves the relevant ones, and answers from those with a sentiment breakdown and the supporting reviews shown underneath.

Up to 500 reviews per app, deduplicated by text before anything else happens. Reviews are chunked at sentence boundaries into roughly 200-character segments and embedded locally, so nothing goes to a paid embedding service. Retrieval is similarity search over a local vector store, scoped to the feature area first when one is given. The answer is assembled by an LLM through a model-agnostic gateway, with retry and backoff for rate limits.

Free to clone and run, which was a constraint rather than an afterthought. The intended user is another PM who wants an answer this afternoon, not a procurement conversation.

03

Key decisions

A confidence threshold on sentiment. The first version counted "it's okay I guess" as positive, which flattered the breakdown. A threshold routes weak signals into an Uncertain bucket instead, and it is adjustable in the sidebar rather than hidden, because how strict to be is the user's call and not mine.

Star ratings first, text analysis second. Where a review carries a rating, the rating is the signal. Text-only reviews fall back to a lexicon-based analyser. Two sources of truth with a stated precedence beats one model guessing at everything.

A model gateway rather than a direct API. Swapping models is a one-line change with no SDK refactor, so the tool runs on a free tier today and can move to a stronger model without touching anything else. It also keeps it free for anyone else to clone.

A local vector store, knowingly temporary. It runs with zero signup, which is the whole point of a tool meant to be cloned and used immediately. It is also not production-ready: no managed hosting, no access controls, unreliable under concurrent load. The right call for a prototype and the first thing to replace for a team.

Local embeddings over a paid API. The pipeline runs offline at 384 dimensions with no external dependency and no per-call cost. The original library had no prebuilt build for the Python version in use, and switching to direct inference removed the dependency rather than working around it.

04

What I found

A clean-looking answer was the wrong answer. The first sentiment breakdown was convincing and inaccurate. Adding the confidence threshold showed that roughly five to ten percent of reviews are genuinely ambiguous. Surfacing that honestly is more useful to a PM than a breakdown implying precision the data cannot support.

The worst bug was silent. The review feed found apps correctly and returned zero reviews, with no error and no explanation. Nothing failed; there was simply nothing there. Terminal logging is what surfaced it, and the fix was to call the platform's own API directly, which turned out to be more reliable anyway.

Environment setup cost more than the product logic. Getting compatible library builds for the Python version in use took longer than writing the retrieval pipeline. That reads as an engineering detail and is not one: it decides how fast a teammate can clone the thing and run it, which makes it a product problem.

Silent failures are the expensive kind. Nothing errored, nothing logged, and the answer was simply built from nothing.

05

What I would do differently

Pin the environment on day one. Lock the Python version and pin every dependency from the first commit. Most of the time lost went to a problem a virtual environment and a lockfile would have prevented.

Add time filtering before anything else. A PM rarely wants all reviews. They want the last thirty days, because the question is usually about reaction to a specific release. That one filter would have made the tool more useful than any model upgrade.

Migrate the store before data accumulates. Moving off the local vector database gets harder the longer it holds data. It was the right prototype choice and the wrong thing to defer.

Treat the review source as the weak link. The feed is unreliable for some regions and apps, and every downstream answer inherits that. A more robust source is worth more than a better prompt.
